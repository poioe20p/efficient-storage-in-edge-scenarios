## 1. Thesis Context

This thesis investigates whether collapsing three traditionally separated
control-plane concerns — **information acquisition** (monitoring), **backend
selection** (load balancing), and **infrastructure adaptation** (auto-scaling)
— into a single SDN controller process eliminates coordination gaps that
degrade service quality during demand shifts.

RQ1 isolates the **information acquisition** dimension of this unification.

---

## 2. Research Question

> How does telemetry delivery cadence — aggregator-paced push versus
> controller-paced polling at three intervals — affect reaction latency
> and transient service quality during demand shifts in a stateful edge
> system?

---

## 3. What Is Being Investigated

The system aggregates raw edge-server telemetry into 10-second summary
windows. The controller can receive these summaries in two ways:

- **Push** (ZMQ): aggregator publishes at window close. Controller sees every window.
- **Poll** (HTTP): controller fetches from aggregator cache at configurable intervals (5 s, 12 s, or 30 s).

The mechanism is **missed windows** — the controller does not see telemetry
between polls:

```
Push:     sees every window (10 s cadence)
          ──[W10]──[W20]──[W30]──[W40]──
          ✅       ✅       ✅       ✅

Poll-30s: sees 1 of every 3 windows
          ──[W10]──[W20]──[W30]──[W40]──
          ❌       ❌       ✅       ❌
          ↑────── blind spot ──────↑
```

If overload appears at W15, Push learns within milliseconds. Poll-30s learns
at t=30 — a 15-second blind spot during which no action is taken.

---

## 4. Why This Question Exists

### 4.1 Purpose

RQ1 tests whether the delivery mechanism measurably affects the controller's
ability to respond. If the blind spot degrades service, the coordination gap
is real and quantifiable. If not, the thesis can bound the problem.

### 4.2 What Each Condition Encodes

| Condition | Delivery | Blind spot | Encodes |
|---|---|---|---|
| **Push** | ZMQ at window close | None | Unified architecture |
| **Poll-5s** | HTTP every 5 s | None (duplicates polls) | Proves mechanism is missed windows, not stale data |
| **Poll-12s** | HTTP every 12 s | Minor | Penalty is gradual, not binary |
| **Poll-30s** | HTTP every 30 s | Major (~2/3 windows missed) | Separated-architecture default |

| `EDGE_CPUS` | 0.30 | 0.15 | 0.15 | **0.15** | Push handles this; v10/v12 proved it |

### 4.4 Why v13 Redesigns the Phases

v12 (EDGE=0.15, STORAGE=0.05, CT=30, `--connect-timeout 5`) was the
definitive campaign planned from the v11 calibration winner (S2+CT5, 5/6
gates in a single pilot pair). At n=3, the configuration proved unstable
(~30% catastrophic failure rate). Root cause: the `compute_spike` phase
(100% `service_pressure` with `window_min=1`) produced extreme per-request
variance, occasionally triggering TCP accept-queue collapse or Poll-30s
under-provisioning. The S2+CT5 calibration was done at n=1 — the single-pair
pilot gave a false sense of reliability.

v13 makes two changes informed by v12's diagnosis:

1. **Redesigned phases**: Shorter stress phases (150s) increase the blind-spot
   fraction from 12-17% to 20% of each stress event. Two `storage_storm`
   phases double-measure the storage cascade — the mechanism where the
   blind-spot penalty is most visible. `compute_spike` is removed entirely,
   eliminating the `window_min=1` variance source.

2. **CT5 removed**: `--connect-timeout 5` is dropped. Without `compute_spike`,
   the accept-queue collapse that CT5 exposed is no longer triggered. TCP-level
   failures appear as high-latency completions rather than `http_status=0`
   timeouts. The thesis narrative emphasizes throughput degradation and tail
   latency as the primary RQ1 signals.

The S2 resource configuration (EDGE=0.15, STORAGE=0.05) is unchanged — it
remains the only calibration point that produces separation between Push and
Poll-30s.

## 5. How It Is Measured

The measurement framework decomposes the coordination gap into metrics
organized by what they measure: **detection failure**, **user impact**,
and **recovery**.

### Detection Failure

| M# | Metric | Source | What it shows |
|----|--------|--------|--------------|
| M1 | Spawn count by type | `node_lifecycle_timings.csv` | Controller's failure to detect overload → fewer nodes |
| M2 | Missed scale-up opportunities | `per_node_stats.csv` | Windows where CPU breached but no action taken |
| M6 | Blind-spot window rate | `blind_spot_windows.csv` | % of breached windows the controller never saw |

### User Impact

| M# | Metric | Source | What it shows |
|----|--------|--------|--------------|
| M3 | Throughput (total requests) | `client_requests.csv` row count | Users completed fewer requests |
| M4 | Timeout rate | `client_requests.csv` http_status=0 | Users experienced failures |
| M5 | Latency (p50, p95, p99, stddev) | `client_requests.csv` latency_s | Users experienced slower responses |
| M7 | Reaction latency | `elasticity_events.csv` | Time from overload onset to spawn decision |

### Recovery

| M# | Metric | Source | What it shows |
|----|--------|--------|--------------|
| M8 | Scale-down timing | `elasticity_events.csv` | How long dynamic nodes persist after demand drops |
| M9 | Controller overhead | `resource_stats.csv` | CPU/RAM cost of telemetry delivery mode |

## 6. Expected Outcomes (v13)

1. **Throughput**: Push and Poll-30s ranges do not overlap. Monotonic gradient
   across modes (Push ≈ Poll-5s > Poll-12s > Poll-30s).

2. **p95 latency**: Poll-30s p95 ≥ 1.15× Push p95. Tail inflation follows the
   polling interval gradient.

3. **Timeout direction**: P30 timeout ≥ Push timeout (direction only; magnitude
   not gated — CT5 removed).

4. **Within-mode stability**: Range ≤ 15K requests within each mode across n=3.
   `storage_storm` and `storage_storm_2` show consistent within-run gap.

5. **G8**: All 12 runs pass (no spawns in cleanup gaps).
