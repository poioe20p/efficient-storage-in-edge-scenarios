## Conclusion

The probe **passes all five G2 sub-gates and G1/G4**. Per-connection VIP_DATA forwarding was active (45,246 installs on lan1 / 38,235 on lan2, **zero** per-client shadowing rules), pooled edge clients (`EDGE_MONGO_MAX_POOL_SIZE=6`, `readPreference=secondaryPreferred`) fanned reads across 4 dynamic + 1 static storage backends per LAN, storage **secondaries sustained 15–21 concurrent client connections each with 60–76% CPU** (post-fix read serving), `NotPrimaryOrSecondary` = **0** across all service logs, and `rho(storage_count, T_db)` was negative on both LANs (−0.534 lan1, −0.431 lan2). Storage scale-out produced genuinely usable read capacity for the first time: DB latency fell from ~286 ms at ≤1 backend to ~25 ms at 5 backends (lan1). This run is a valid **control group for the Approach B validation**; a control-group rerun with the knobs unset (G3) remains for byte-identical comparison.

## Main Points

- **Per-connection mode active, guard correct**: 45,246 (lan1) + 38,235 (lan2) per-connection forward-rule installs with distinct `tcp_src`; 0 per-client rules; 3 non-TCP guard drops per LAN (G2.1 ✓).
- **Fan-out works**: a single edge's connections land on 3–5 different backends (e.g. client `10.0.0.2` → local backends {10.0.0.4, .6, .9}, and all 5 backends via the peer VIP). Every secondary shows 15.2–20.9 avg concurrent connections (G2.2 ✓).
- **Established connections survive**: binding-map drops occur only during post-episode scale-down (lan1 20:58:32+, lan2 20:59:30+), never mid-episode; no mid-connection DNAT break, no NotPrimary storm (G2.3 ✓).
- **No NotPrimary/13436** anywhere (G2.4 ✓).
- **Storage scale-out is now measurable**: negative rho both LANs; T_db_avg 286→25 ms (lan1), 305→115 ms (lan2) from ≤1 → 5 backends; secondaries serve (G2.5 ✓).
- **G1/G4 confirmed**: static edges run `secondaryPreferred` (MongoClient creation logs show `readPref=secondaryPreferred` on both VIP clients); writes bypass the VIP (direct `10.0.0.4:27018`, `pool=2`), content_update 99.04% success.
- **Correction to the run description**: storage scaled to **5 backends/LAN at peak (4 dynamic + 1 static)**, not 4 (the `ACTION_BUDGET_PER_TIER=4` storage budget was fully consumed: 4 dynamic storage per LAN; `resource_stats.csv` `storage_count` max = 5).
- **Errors are timeouts, not the old defect**: 586/46,053 episode errors (1.27%) are `http_status=0` (333 immediate + 253 × ~30 s timeouts), with a 322-error transient at 20:51 coinciding with compute `dyn2` scale-down. No 13436-class errors.

## Practical Interpretation (control-group framing)

This probe run is the **control for the Approach B fix validation** and establishes, with concrete evidence:

1. **Storage scale-out now yields usable read capacity.** T_db collapses from ~286 ms (≤1 backend) to ~25 ms (5 backends) on lan1 (2.7–11.4× across LANs), rho(storage, T_db) < 0 on both LANs, storage CPU tracks the added capacity — the DB-latency relief is no longer purely compute-driven.
2. **Secondaries serve reads.** Each secondary sustains 15–21 concurrent client connections and 60–76% CPU during the episode with zero NotPrimary rejections — the pre-fix signature (connections opened then rejected, ~zero serving) is inverted.
3. **Fan-out is real and balanced.** Per-connection mode distributes an edge's pooled connections across 3–5 backends (edges × pool = 24×6 = 144 connection slots ≫ 10 backends), so serving capacity scales beyond `min(edges, storage)`.
4. **No NotPrimary storm.** 0 × 13436; the only failures are client timeouts (1.27% episode tail) and a scale-down transient — normal platform behavior, not the defect.
5. **Write path untouched.** Writes bypass the VIP to the primary; 99.04% success under the episode.

The probe therefore clears the "make-or-break" G2 gate; the campaign can proceed to G3 (knobs unset → byte-identical `primary` path) as the complementary control.
