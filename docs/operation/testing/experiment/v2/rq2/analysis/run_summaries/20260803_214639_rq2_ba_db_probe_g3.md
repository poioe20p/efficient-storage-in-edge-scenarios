## Mechanism (default path, per finding §2/§7)

- **Per-client flows, single pinned backend**: flows keyed `client=IP:*` (wildcard `tcp_src`), **0** per-connection rules (controller log: 0 matches for per-connection/tcp_src; 16,700 lan1 / 16,486 lan2 "per-client forward rule installed"). Each edge's MongoDB connection to the data VIP is DNAT'd to ONE backend chosen round-robin on SYN; the flow idle-expires (10 s) / hard-expires (**120 s**) → re-pin every ~120 s via round-robin. No binding map, no per-connection mode.
- **Primary-pref read client**: `Created MongoClient for lan1 … mongodb://10.0.0.254:27018/ (maxIdleTimeMS=30000 readPref=primary)` and the same for the peer VIP — with `directConnection` the driver treats the pinned backend as a single server with `secondaryOk=false`; when that backend is a secondary, `find` is rejected server-side: `NotPrimaryOrSecondary` (13436).
- **Consequence**: an edge pinned to a secondary **stops serving successfully** — n1's flow timeline during the episode (re-pin every 120 s): 21:46:41→10.0.0.4 (primary, serves 21:47–21:48), 21:48:41→10.0.0.6, 21:50:43→10.0.0.6, 21:52:43→10.0.0.9, 21:54:43→10.0.0.12, 21:56:44→10.0.0.7 — i.e. **pinned to secondaries for most of the episode**, matching its **0-request minutes (21:49, 21:50, 21:52, 21:53)**. The 512 episode client errors (unknown backend) are these dropped/hung requests; the 25 logged 13436 appear only at demand-drop when, at low load, the fast server-side reject surfaces directly as an edge `db_failure` → HTTP 503.
- **The 503 burst (22:00:52–22:01:06)**: at demand-drop start, storage scale-down churn deletes/re-installs flows. n1's local flow re-pinned at 22:00:22 to **10.0.0.12 (dyn7, secondary)**; n1's next local read (22:00:52) hit the secondary → instant NotPrimary → 503; 25 consecutive failures over 13 s (reads every ~0.5–1 s), then the flow re-pinned (22:01:09 → 10.0.0.6) and reads recovered by 22:01:07.
- **Writes unchanged (G4)**: write client is direct `mongodb://10.0.0.4:27018/ (pool=2)` — never through the VIP, never to secondaries. All 25 rejections are `find`; `content_update` 99.31 % ok.
- **Classifier/scale actions**: 4× DataAlert + 4× ComputeAlert per LAN (interleaved, storage-first at 21:48:01), driving 4 dynamic storage + 4 dynamic compute per LAN to budget 4/4; storage scale-down from 21:59:13 with retry churn (Caveat #6).

## Anomalies / Caveats

1. **Why 25 errors, all on `edge_server_n1`, none on n2/dyn edges**: with per-client flows + pool=1 only ONE edge's single connection is pinned to a secondary at a time, and the burst is a round-robin re-pin lottery during scale-down churn — n1's flow landed on a secondary (10.0.0.12) while it was actively issuing local reads at demand-drop start; the other edges' re-pins landed on working backends (or their pinned-window failures surfaced as client timeouts, not logged 13436). Not a code asymmetry — the run's config is uniform.
2. **Errors at demand-drop start, not during the episode**: during the episode, secondary-pinned service drops manifested as client-side timeouts/connection failures (512 `http_status=0`, unknown backend) because high load masks the fast reject behind 30 s client timeouts; at low demand-drop load the instant server-side reject surfaces directly as an edge-logged `NotPrimaryError` → 503. The 13436 count (25) is therefore a *lower bound* on how often reads hit secondaries.
3. **Low absolute 13436 count**: the rejections are a small, bursty subset (25/541 = 4.6 % of all client errors); the dominant client-visible symptom of the defect in this run is the timeout rate (~1.3 %) plus the 4.4× higher episode T_db p50. The control-pair contrast (25 vs 0) is the clean defect signature.
4. **Fast-fail artifact**: every reject is `last_cmd_s` 0.3–1.5 ms — instantaneous. Rejected reads never queue, so they are excluded from T_db medians while lowering the primary's concurrency → the apparent T_db drop (468→165 ms) and the negative rho are **not** genuine serving relief. This is why rho must NOT be read as "scale-out works" in G3; the honest discriminator vs §9 is the T_db floor (165–174 vs 20–89 ms at 5 backends) and the NotPrimary count.
5. **Secondaries burn CPU without serving**: 37–80 % avg CPU on secondaries (replication + rejected-command overhead) — a CPU-only reading would be misled; the finding-§3 storage-telemetry limitation persists (per-node `request_count` is an activity flag; db_read/cmd columns unpopulated for storage).
6. **Storage scale-down retry churn**: `dyn8` (lan2) ×5 and `dyn1` (lan1) ×4 remove attempts vs only 3 (lan1) / 2 (lan2) completed cleanups; `storage_count` = 2 at run end (scale-down still converging when the run completed). Likely connected to the flow-churn/pinning churn that also produced the 503 burst; worth a follow-up if storage scale-down reliability matters for RQ2.

## Practical Interpretation (negative-control framing)

This run is the **negative arm** that completes the Approach B control pair:

1. **The default path reproduces the pre-fix defect exactly.** Per-client pinning (single connection per edge), `readPreference=primary`, and `NotPrimaryOrSecondary` (13436) returning on secondaries — the §8 G3 contract, byte-identical.
2. **Storage scale-out still yields ~zero usable read capacity.** Secondaries hold connections and burn replication CPU but never serve a successful read; the T_db floor at 5 backends (165–174 ms) is ~8× higher than §9's, and the apparent "relief" is a fast-fail artifact.
3. **The fix — not the workload — is what changed behavior.** Same phases, same thresholds, same launch config, same 5-backend scale-out, nearly identical overall error rate (~1.28 % vs 1.27 %); the ONLY differences are the three knobs and everything that follows (0 vs 25 NotPrimary; secondaries serving vs rejecting; T_db floor 25 vs 165 ms).
4. **The episode latency cost of the defect is large and measurable**: T_db p50 156–184 ms (~4.4× §9), client p95/p99 1.86 s/3.97 s, throughput 66.7 vs 76.8 req/s — strong motivation for the fix and a clean RQ2 "before/after" headline.
5. **Writes are untouched (G4)**: 99.31 % content_update success, direct-to-primary, no write-side NotPrimary.

**Overall verdict**: G3 gate **✅ MET**; the control pair (§9 positive, G3 negative) is **consistent and complete**; G1–G4 all satisfied. **The platform is safe to move forward with the RQ2 campaign.**
